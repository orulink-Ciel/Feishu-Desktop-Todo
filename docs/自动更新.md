# 轻列便签：自动更新

从 0.1.2 开始，桌面应用启动 10 秒后检查更新，保持运行时每 6 小时检查一次。发现新版本会显示提示，用户点击“下载安装并重启”才下载安装。设置中可以查看当前版本、手动检查，以及找回稍后处理的更新提示。

0.1.5 在设置中加入“开机自启动”，可查看并修改 Windows 或 macOS 的系统登录启动状态；此设置独立于飞书登录。浏览器预览只模拟开关，真实系统注册仅在桌面应用中生效。安装包与自动更新通道包含 Windows 通用版、Windows 公司版、Apple 芯片 Mac 和 Intel Mac。

0.1.4 新增独立周历页面，按日期查看一周任务截止安排；更新三套主题视觉和主题预览，并让主题、设置面板在选择后或点击外部时自动收起。应用名称和图标同步更新；[下载 0.1.4 内部试用版](https://github.com/orulink-Ciel/Feishu-Desktop-Todo/releases/tag/v0.1.4-preview.1)，提供 Windows 与两种 Mac 安装包。

0.1.3 修复未登录或授权失效时显示上次账号姓名的问题。此时底栏显示“未连接飞书”，不读取旧账号任务缓存；缓存按账号保留，重新授权后恢复对应账号的数据。0.1.2 用户可直接检查更新；[0.1.3 下载页](https://github.com/orulink-Ciel/Feishu-Desktop-Todo/releases/tag/v0.1.3-preview.1)。

0.1.1 及更早版本需要手动安装一次 0.1.2 或更新版本。更新保留当前系统用户的飞书授权、SQLite 缓存、主题与窗口位置；安装前主动保存窗口状态。任务正在同步或提交时，安装按钮暂不可用。下载安装期间显示进度，并阻止继续操作任务。

## 四个更新通道

| 通道 | 使用的更新包 |
| --- | --- |
| `windows-x86_64` | Windows 通用 NSIS 安装包 |
| `windows-internal-x86_64` | 预设公司值日来源的 Windows NSIS 安装包 |
| `darwin-aarch64` | Apple 芯片 Mac 的 `.app.tar.gz` |
| `darwin-x86_64` | Intel Mac 的 `.app.tar.gz` |

通道由本机应用编译后的值日配置、操作系统和 CPU 架构决定。公司版不会安装通用版，Mac 架构不会混用。Mac 公司定制版使用独立的 `darwin-internal-*` 通道，目前没有对应更新包，应由管理员单独发布后启用。

安装包仍在版本发布页供首次下载；固定的 [更新入口](https://github.com/orulink-Ciel/Feishu-Desktop-Todo/releases/download/desktop-updates/latest.json) 仅保存清单，将每个通道指向已发布的版本包。试用版不依赖 GitHub 的“latest”判定。

## 签名与失败处理

使用 [Tauri Updater](https://v2.tauri.app/plugin/updater/) 验证更新签名。公钥在应用配置中，私钥只用于打包签名，不进入源码、安装包或更新清单。GitHub 仓库 Secrets 保存 `TAURI_SIGNING_PRIVATE_KEY` 与 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`；公司资源映射另存 `FEISHU_TODO_DUTY_CONFIG`，其中仅允许文档和表格资源映射，不放人员数据或授权凭据。

签名校验发生在下载阶段，失败后不会启动安装程序。检查或下载失败时保留当前版本，用户可重试。安装成功但重新启动失败时，界面提供“重新启动”，不会重复安装；也可以退出再打开。

更新包签名与 Windows 商业代码签名、Apple Developer ID、公证是不同机制。目前更新包具备 Tauri 签名，Windows 仍无商业签名，Mac 仍为临时签名、未公证。

管理员需要备份签名私钥及密码；丢失后无法为已安装用户继续签发可信更新。换一台开发电脑时需要导入原密钥，不能直接生成新密钥替换公钥。

## 发布新版本

先将 `package.json`、锁文件、`src-tauri/Cargo.toml`、`Cargo.lock` 与 `tauri.conf.json` 升到同一个新版本，例如 `0.1.7`，并在发布脚本中填写本次用户更新说明。提交到发布分支，在 GitHub Actions 的 **Desktop preview packages** 中选择该分支运行：

1. 勾选发布选项，填写 `v0.1.7-preview.1` 等与源码匹配的试用标签。
2. 四个构建任务分别验证测试、格式、Clippy、安装包和内置 CLI；Windows 验证实际安装后的资源，Mac 验证应用签名与 DMG。
3. 全部通过后，发布任务合并四平台 artifact。缺少任何通道、签名文件或包都会停止发布。
4. 先上传版本包并核对 GitHub SHA-256 摘要，发布版本，然后更新固定入口中的 `latest.json`。

普通推送只构建，不发布。发布任务串行运行，拒绝用旧版本覆盖较新的更新清单。已发布的版本包不可覆盖；需要修复时增加版本号重新发布。失败构建不会更新清单。

创建草稿后使用 GitHub POST 响应中的发布 ID，并按 ID 读取上传结果，避免刚创建的草稿暂时未出现在发布列表时中断。已存在的版本继续执行提交和文件摘要校验。

公司资源配置只从 Secret 写入构建目录，Git 继续使用示例配置。下载的公司 Windows 包不包含飞书应用密钥或用户令牌，每位同事仍需配置应用并扫码授权。

## 验证范围

前端覆盖延迟检查、六小时间隔、请求防重、检查失败重试、下载或签名失败不安装、任务提交期间禁止安装、保存窗口状态后安装，以及重启失败只重试重启。发布脚本覆盖缺少通道、公司包与通用包隔离、版本不匹配的拒绝行为。

0.1.3 已发布，固定入口包含上述四个通道。[本次 Actions](https://github.com/orulink-Ciel/Feishu-Desktop-Todo/actions/runs/38342354190) 的四平台构建、发布和四个平台的线上包下载签名验证均通过。各诊断记录明确标记 `signatureVerified: true`、`installed: false`，未执行实际升级。发布标签固定在安装包源提交 `f65ae66`，后续草稿 ID 读取调整仅影响发布脚本。

登录修复验证：41 项前端测试、21 项 Rust 测试通过；2 项真实飞书 API 测试未运行，避免改动业务任务。生产界面以模拟原生桥接分别验证未登录、残留旧姓名、正常只读账号，未登录界面已确认显示“未连接飞书”。真实账号注销及跨版本安装仍需用户实机验证。

签名下载通过不等于全部实机升级已验收。下一次更高版本还应在真实 Windows 和 Mac 上确认安装、重启及设置保留。

原生程序的 `--check-update` 诊断会读取固定更新入口、下载本通道当前发布的包，并通过实际 Updater 校验签名；它不会安装、重启或读取用户账户和任务缓存。该诊断为校验当前包临时忽略版本大小比较，正常界面仍只提示更高版本。
